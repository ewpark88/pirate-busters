---
description: 설계서 변경을 개발 계획서에 반영한다 (ADR-008, ADR-030)
---
설계서 변경을 개발 계획서에 반영한다. 설계서가 기준이고 계획서가 따른다(CLAUDE.md 절대 규칙 12). 설계서 자체는 고치지 않는다.

1. `dart run tool/check_doc_sync.dart` 로 상태를 확인한다. 통과하고 사용자가 전체 점검을 요청하지 않았으면 “동기화됨”이라고 보고하고 끝낸다. (해시만 보는 검사이므로, 전체 점검 요청이면 7번까지 한다.)
2. `git diff` 와 `git log -p -- "Pirate Busters 게임 설계서.md"` 로 계획서 표시 해시 이후 바뀐 절(§)을 찾는다.
3. 바뀐 절마다: 계획서에서 그 §를 참조하는 작업·완료 조건·수치·범위를 설계서 문구에 맞게 고친다. 계획서에 담당 단계가 없는 설계서 기능은 단계를 정해 넣는다. 새 기능·이벤트·메뉴는 기존 단계에 끼워 넣지 않고 12장 ‘추가 단계’ 끝에 `A<n>` 단계로 붙인다(CLAUDE.md 절대 규칙 11, ADR-024). 기존 기능의 수치·규칙 변경은 그 단계에서 고치되, 끝난 단계의 코드를 다시 고쳐야 하면 그 작업도 `A<n>` 으로 만든다. 없어진 기능은 지운다.
4. 계획서가 ADR 로 설계서와 다르게 적혀 있던 곳이 있으면 설계서 문구로 되돌리고, 그 차이를 사용자에게 알린다(설계서를 고칠지는 사용자가 정한다).
5. 설계서 안의 모순·빈 곳(서로 다른 수치, 정의 안 된 값)은 고치지 말고 수정안과 함께 목록으로 보고한다.
6. 이미 끝난 단계나 현재 단계에 영향이 있으면 표(절 / 영향 단계 / 코드 수정 필요 여부)로 사용자에게 알린다.
7. 계획서 머리의 `설계서 동기화:` 해시와 날짜를 갱신하고, 계획 변경이 크면 `/adr` 로 ADR 을 남긴다. 설계서 변경과 계획서 변경은 같은 커밋에 넣는다.
8. `dart run tool/check_doc_sync.dart` 가 통과하는지 확인한다.

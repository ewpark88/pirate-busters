# 결정 기록 (ADR)

새 패키지 추가, 규칙 변경, 계획 변경은 여기에 남긴다. 형식: 배경 → 결정 → 대안 → 영향.

## ADR-001 모노레포는 Dart pub workspace (2026-09-29)
- **배경:** 설계서 §7.3 의 패키지 구조(`pb_sim`, `pb_ai`, `pb_data`, `app`, `sim_runner`)를 한 저장소에서 관리해야 한다.
- **결정:** Dart 3.12 에 내장된 pub workspace 를 쓴다. 루트 `pubspec.yaml` 이 멤버를 나열하고, lock 파일은 루트에 하나만 둔다.
- **대안:** melos. 설치할 도구가 하나 늘고, 지금 규모에서는 workspace 로 충분하다.
- **영향:** `flutter pub get` 은 루트에서 한 번만 실행한다. 테스트는 패키지 디렉터리에서 `dart test` 로 돌린다(`tool/verify.sh`).

## ADR-002 패키지 의존 방향: pb_sim 이 중심 (2026-09-29)
- **결정:** `pb_sim` 은 워크스페이스 패키지에 의존하지 않는다. `pb_ai`, `pb_data` 는 `pb_sim` 에만 의존한다. `app`, `sim_runner` 가 모두를 조립한다. `tool/architecture/rules.dart` 가 검사한다.
- **이유:** 전투 엔진이 도메인이고, 데이터(JSON)는 어댑터다(mozzi `domain ← data` 와 같은 방향). `pb_data` 가 JSON 을 `pb_sim` 의 정수 정의로 바꾸므로 `pb_sim` 은 JSON 을 모른다.
- **영향:** 개발 계획서 §2.1 의 의존 방향 표기를 이 결정에 맞게 고쳤다.

## ADR-003 결정론을 자동으로 검사 (2026-09-29)
- **결정:** `pb_sim`, `pb_ai` 의 lib 에서 `dart:math`, `dart:async` import, `double`/`num`/`toDouble`/`Random`/`DateTime`/`Stopwatch`/`identityHashCode` 식별자, 실수 리터럴, `/` 연산자를 금지한다. 주석과 문자열은 검사하지 않는다.
- **이유:** 설계서 §7.1, §12 “시뮬레이션 패키지에서 double 사용을 린트로 금지”. Dart 의 `int / int` 는 `double` 을 만들기 때문에 `/` 도 막는다(`~/` 사용).
- **대안:** `custom_lint` 플러그인. 의존성과 설정이 늘어나므로, mozzi 처럼 스크립트 검사로 시작한다.
- **한계:** `Map` 순회 순서 같은 규칙은 자동으로 못 잡는다 → 리뷰와 골든 해시 테스트로 잡는다.

## ADR-004 mozzi 코드는 복사 후 수정 (2026-09-29)
- **결정:** 공용 패키지로 분리하지 않고 필요한 파일을 복사해 고친다. 목록은 `docs/MOZZI_REUSE.md`.
- **이유:** mozzi 코드는 `double` 기반이고 GDD 수치와 엮여 있어 그대로 공유할 수 없다. 두 게임 모두 진행 중이라 공용 패키지의 API 를 고정하기 이르다.
- **대안:** 공용 패키지 `mozzi_kit`. 두 게임에서 안정되면(정식 출시 이후) 다시 검토한다.

## ADR-005 로컬 저장소는 Hive CE (2026-09-29)
- **결정:** 설계서 §7.4 의 “Isar 또는 Hive” 중 `hive_ce` 를 쓴다. M7 에서 추가한다.
- **이유:** mozzi 와 같은 패키지다. Isar 는 원 저장소 유지보수가 멈췄다.

## ADR-006 Android 먼저 (2026-09-29)
- **결정:** MVP 와 정식 출시는 Android 로 한다. iOS 는 출시 이후 검토한다.
- **이유:** 비공개 테스트가 Play 기준이고(설계서 §11.2), 계정은 Google Play Games Services(§7.4)다. mozzi 와 같은 방침이다.
- **영향:** `app` 은 android 플랫폼만 생성했다. applicationId 는 `com.repo.pirate_busters`.

## ADR-007 리플레이·커맨드·설계도 직렬화는 pb_sim 이 갖는다 (2026-09-29)
- **배경:** 개발 계획서 M1 은 `pb_sim` 에 리플레이 JSON 저장·읽기를 둔다. ADR-002 는 “`pb_sim` 은 JSON 을 모른다”고 적었다.
- **결정:** 엔진 자체의 산출물(커맨드, 설계도, 리플레이)은 `pb_sim` 이 `toJson()`/`fromJson(Map)` 을 갖는다. `dart:convert` 는 쓰지 않고 문자열 변환은 호출하는 쪽이 한다. 해적·블록·스테이지 같은 **콘텐츠 데이터** JSON 은 계속 `pb_data` 가 읽어 `pb_sim` 정의로 바꾼다.
- **이유:** 리플레이는 PvP·버그 재현·부정 검사에서 엔진과 한 몸으로 움직인다(설계서 §7.2). 형식 버전을 엔진과 같이 올려야 한다.
- **대안:** 코덱을 `pb_data` 에 둔다. M1 이 `pb_data` 까지 건드리고 형식과 엔진이 멀어진다.
- **영향:** ADR-002 의 “JSON 을 모른다”는 콘텐츠 데이터에 한정한다. 리플레이 JSON 에는 `version` 필드를 둔다(현재 1).

## ADR-008 설계서가 바뀌면 개발 계획서를 같이 고친다 (2026-09-29)
- **배경:** 게임 설계서는 계속 갱신된다. 개발 계획서는 설계서를 작업 단위로 쪼갠 문서라, 설계서만 바뀌면 에이전트가 낡은 계획대로 작업하게 된다.
- **결정:** 계획서 머리에 `설계서 동기화: <해시>` 를 둔다. 해시는 설계서 본문(LF 정규화)의 FNV-1a 32비트 값이다. `tool/check_doc_sync.dart` 가 비교하고 `verify` 4/5 단계에서 돌린다. 값이 다르면 계획서에 변경을 반영한 뒤에만 해시를 갱신한다(절차: CLAUDE.md).
- **대안:** 규칙 문장만 둔다. 설계서를 사용자가 직접 고치므로 에이전트가 변경을 놓치기 쉽다. git 커밋 해시 비교는 커밋 전 수정과 리베이스에 약하다.
- **영향:** 설계서만 고친 상태에서는 verify 가 실패한다. `/step-start` 는 이 검사부터 한다.

## ADR-009 설계서 배 이동(§2.6, §5.5) 을 계획에 넣는다 (2026-09-29)
- **배경:** 설계서에 배 좌우 이동(전진·후퇴 한계, `MOVE` 커맨드, 거리 상성, AI 회피)이 추가됐고 MVP 범위(§11.1)에도 들어갔다.
- **결정:** 시뮬 쪽 이동과 `MOVE` 커맨드는 M2 에 넣는다. 탄도·충돌을 처음 만들 때 배가 움직이는 것을 전제로 해야 나중에 고치지 않는다. 침수 감속·폭풍 한계는 M3, 버튼·한계선 표시는 M4, 속도 요인·거리 상성은 M5, AI 이동은 M6, 나머지 선형 속도는 R2, 지옥 회피는 R3 에 둔다.
- **대안:** 이동 전체를 M5(선형·건조와 같이)로 미룬다. M2 의 탄도·충돌을 고정 위치로 만들었다가 다시 고쳐야 한다.
- **영향:** 완료된 M1 의 `Command` 에 `MOVE` 가 없다 → M2 에서 추가하고 리플레이 형식을 확인한다. M2 작업량이 늘어 MVP 일정(6주)이 밀릴 수 있다.

## ADR-010 M2 전투 판정 구조와 임시 수치 (2026-09-29)
- **배경:** M2(탄도·타격·붕괴)를 만들려면 해적이 탈 자리, 해적 수치, 좌표계가 필요하다. 설계서에 없는 수치도 있다.
- **결정:**
  - 선실 모듈만 M5 에서 M2 로 당긴다. 설계도에 `cabins: [[x, y], …]` 를 두고, 입력 순서가 슬롯 번호다. 개수는 선형의 선실 수와 같아야 하고 블록 위에 있어야 한다.
  - 해적은 선실 칸 **안**에 있다. 선실 블록이 방패라 직격은 블록이 받고, 해적은 폭발 반경 피해만 받는다. 선실 블록이 부서지거나 무너지면 최대 HP 20% 피해를 입고 바다로 떨어진다. 선실이 없는 채로 돌아온 해적은 드러나 있어 직격에 맞는다(사용자 결정).
  - 거리 24칸(16~32)은 **뱃머리 사이 간격**이다(사용자 결정). 설계도는 뱃머리가 +x 인 로컬 격자로 짓고 오른쪽 진영은 좌우를 뒤집는다. FIRE 각도도 “상대 쪽 수평 = 0°”로 진영마다 뒤집는다.
  - 해적 수치는 M5 `pb_data` 전까지 `PirateSpec`/`PirateCatalog` 으로 넘긴다. 리플레이는 덱 id 만 담고 재생할 때 카탈로그를 받는다.
  - 리플레이 형식 v2(선실·바람·MOVE). v1 은 읽지 않는다(배포된 리플레이가 없다).
  - 교대 대기열은 선형과 무관하게 “덱에서 선실 수를 넘는 해적”으로 만든다.
- **임시 수치 (설계서에 없음, 밸런스 단계에서 조정):** 중력 36칸/초², 최대 탄속 40칸/초(45° 로 30칸이면 1.3초), 폭발 가장자리 50% 피해, 손상 단계 2/3·1/3 경계, 헤엄치는 해적 위치는 뱃머리 1칸 앞 해수면이고 폭발·물보라 1칸(또는 폭발 반경) 안이면 즉사, 교대 해적은 재장전부터 시작, 탄은 쏜 진영 배에 닿지 않음, 바다에 떨어진 탄은 블록을 다치게 하지 않음, 해수면 = 용골 바닥(흘수선은 M3).
- **대안:** 선실 없이 해적을 추상 슬롯으로만 둔다. 선실 파괴·낙하·헤엄 카운터 플레이(설계서 §2.3)를 M2 에서 검증할 수 없다.
- **영향:** 골든 해시가 바뀌었다(2447913407 → 190143163). 설계서 §3.1 “슬롯이 6개 이상이면 … 교대 대기열” 과 계획서 M2 “교대 대기열” 의 범위가 어긋난다 → 사용자 확인 필요.

## ADR-011 턴제 전환에 맞춰 계획을 다시 짠다 (2026-09-29)
- **배경:** 설계서가 실시간 포격전에서 턴제(30초 턴, 턴당 이동·발사 2회, 8분 경기 시계, 쿨다운 턴, 연료, 누적 침수량, 시간 판정)로 바뀌었다. 한국어·영어 동시 지원(§14)과 화면 설계(§13)도 추가됐다.
- **결정:**
  - M2 = 턴 루프·탄도·타격·붕괴, M3 = 이동·연료·파도·침수·시간 판정, M4 = 렌더·입력·턴 UI·다국어 기반, M5 = 해적 쿨다운·모듈 9종(연료통)·건조·선원 편성, M6 = AI 턴 운영, M7 = 캠페인·화면(§13)·튜토리얼 3판·출시 준비. 설계서 §11.1 의 주차 계획은 이 순서로 옮겼다(계획서 §4).
  - 다국어 규칙을 CLAUDE.md 절대 규칙 10 으로 넣는다(설계서 §14.5 가 요구). ARB 키 검사는 M4 에서 verify·CI 에 붙인다.
  - ADR-009 의 이동 배치(실시간 `MOVE dir`, 관성, 회피)와 ADR-010 의 일부(뱃머리 간격 24칸, 헤엄 4초, 재장전 틱)는 이 결정으로 대체한다.
- **작업 중인 M2 코드(`feat/M2-ballistics`, 커밋 전)에 주는 영향:**
  - 그대로 쓴다: 월드 좌표·`ShipFrame`, 포물선 탄도, DDA 충돌, 블록 피해·손상 단계, 원형 폭발, 지지 구조 BFS, 선실·`Crew` 뼈대, `PirateSpec`/`PirateCatalog`, 이벤트 스트림.
  - 다시 짠다: `Command`(틱 → 턴 묶음, `END_TURN`, `MOVE(dx)`), `Match.step`(턴 루프·타이머·경기 시계), 재장전 틱 → 쿨다운 턴, 헤엄 4초 → 다음 내 턴 시작 복귀, 파괴 0% → 격침 20% 미만, 턴당 바람, 리플레이(턴 묶음 목록).
  - M3 로 옮긴다: `ShipMotion`(관성 이동 → 연료·dx 이동), 시작 간격 24 → 16칸.
- **대안:** 실시간 M2 를 먼저 끝내고 나중에 턴제로 고친다. 커맨드·리플레이·해시 형식을 두 번 바꾸게 된다.
- **영향:** MVP 범위가 늘어 6주 일정이 밀릴 수 있다. 설계서에서 확인할 것 4가지를 계획서 11장에 적었다(경기 시계와 결정론, AI 생각 연출 시간, 교대 대기열 범위, 실시간 표현 잔재).

## ADR-012 교대 대기열 → 출전 코스트, 8분 시계 → 30턴 제한 (2026-09-29)
- **배경:** 사용자 기획 변경. 교대 대기열은 필요 없고, 출전은 최대 7명, 경기 길이는 시간 대신 턴 수로 제한한다.
- **결정 (설계서에 반영, 사용자 지시로 직접 수정):**
  - 해적 등급을 노멀·매직·레어·전설·신화 5단계로 바꾸고 코스트를 3·4·5·6·8 로 둔다. 기존 등급은 일반→노멀, 희귀→매직, 영웅→레어, 전설→전설로 옮겼고 신화는 시즌 해적부터 쓴다.
  - 출전 코스트 한도는 **선형 레벨**에 따라 오른다(Lv1 15, 레벨당 +2, Lv10 33). 인원은 선실 수 이하, 최대 7명. 교대 대기열은 없다(설계서 §3.1, §4.5).
  - 한 판은 양쪽 합쳐 30턴(각자 15턴), 턴 시간 25초. 폭풍 타임은 27~30턴(폭풍 중 턴 시간 20초), AI 시간 판정 모드는 22턴부터.
  - 갤리온 Lv10 특성 “선실 +1”은 7명 상한과 맞지 않아 “선체 블록 HP +10%”로 바꿨다(예시 값).
- **이유:** 턴 수 제한은 실제 시간이 판정에 들어가지 않아 결정론 문제(계획서 11장)가 사라진다. 코스트는 강한 해적을 몇 명 태울지를 편성의 선택으로 만든다.
- **대안:** 코스트 한도를 선장(플레이어) 레벨에 묶는다. 선실 배치는 배의 속성이라 선형 레벨을 골랐다.
- **영향:** M2 에 출전 코스트 검증이 들어가고 교대 대기열 코드는 지운다. 레벨업 카드 표의 등급 배수도 새 이름(매직 ÷2, 레어 ÷5, 전설 ÷10, 신화 ÷20)으로 바꿨다.

## ADR-013 등급 이름 유지, 출전 코스트 한도는 플레이어 레벨 (2026-09-29)
- **배경:** ADR-012 의 등급 이름(노멀·매직·레어)과 선형 레벨 기준 한도를 사용자가 되돌렸다.
- **결정:** 등급은 일반·희귀·영웅·전설·신화(코스트 3·4·5·6·8). 출전 코스트 한도는 **플레이어 레벨**(1~20)에 따라 Lv1 15, 레벨마다 +1(Lv20 34). 플레이어 경험치는 승리 30·패배/무승부 10·캠페인 첫 클리어 +20, 다음 레벨 필요량 100 × Lv (예시 값, Remote Config). 선형 업그레이드는 한도와 관계없다. 최대 30턴·턴 25초는 언제든 바뀔 수 있는 값으로 두고 설정값으로 구현한다.

## ADR-017 캠페인 확장: 해역당 12스테이지·중간 보스·3모드 (2026-09-29)
- **배경:** 사용자 요청. 6해역 × (5스테이지 + 보스) = 36판은 정식 출시 캠페인으로 너무 작았다.

- **영향:** R3 가 ‘해역 2~6’ 에서 ‘캠페인 완성’ 으로 커졌다(스테이지 72, 중간 보스 6, 모드 3). 대사 ARB 키가 크게 늘어난다. `sim_runner` 로 모드별 난이도 곡선을 확인해야 한다. M3~M7 코드에는 영향이 없다.

## ADR-018 시작 해적 2명과 캠페인 해적 보상 (2026-09-29)
- **배경:** 사용자 요청. 설계서에 시작 해적이 없었고(“첫 판은 일반 4명”만 있음), 캠페인에서 해적을 얻는 규칙이 “세력 종족 카드”뿐이었다.
- **결정:**
  - 시작 해적은 옥토(투척)·톡(지원) 2명. 해역 1 확정 보상으로 수리·폴리·팡·샤키를 주어 덱 4칸과 계열을 채운다 (설계서 §4.6).
  - 해역 2~6 보스는 세력 종족의 일반·희귀 1명을 확정으로 준다(본즈·윙·핑구·젤리, §15.3).
  - 스테이지 3·7·10·중간 보스·보스 첫 클리어에 확률 보상. 초반 일반·희귀, 뒤로 갈수록 영웅, 전설은 0~1.5% (`reward_*`).

## ADR-019 등급별 최대 레벨과 선원 레벨에 비례하는 선체 내구도 (2026-09-29)
- **배경:** 사용자 요청. 해적 레벨은 모든 등급이 Lv1~10(+8%/Lv, 최대 +72%)이었는데, 배 내구도는 선형 업그레이드 +3%/Lv(최대 +27%)뿐이었다. 레벨이 오를수록 피해가 내구도를 크게 앞질러 후반 전투가 몇 발에 끝나는 구조였다.
- **결정:**
  - 해적 최대 레벨을 등급별로 둔다: 일반 15 · 희귀 14 · 영웅 13 · 전설·신화 12. 레벨당 피해·체력 +6%. 높은 등급은 효과, 낮은 등급은 레벨 상한으로 강해진다 (설계서 §4.4). 레벨업 비용 표를 Lv15 까지 늘렸다 (§13.7).
  - 블록 내구도 = 재질 × 선원 레벨 보정(1 + 6% × (출전 해적 평균 레벨 − 1)) × 선형 업그레이드 보정(+3%/Lv). 해적 피해와 같은 곡선이라 같은 레벨끼리는 판 길이가 비슷하다 (§3.5).
  - 보정은 매치 시작 때 ‰ 정수로 pb_sim 에 넘긴다. 격침·동률 판정은 내구도 비율로 한다.
  - 캠페인 적 해적 레벨을 새 상한에 맞추고(일반 1~6, 어려움 4~10, 지옥 8~15) 적 선형 레벨을 더했다 (§6.1).
  - 데이터의 `growth` 에서 실수 성장률·`maxLv` 를 빼고 특성 키만 둔다 (§4.3).
- **대안:** 모든 등급 같은 최대 레벨 — 사용자가 원한 “높은 레벨의 희귀·영웅이 전설보다 강할 수 있음”이 약해진다. 선형 업그레이드만으로 내구도를 키움 — 해적만 키운 플레이어의 배가 녹고, 업그레이드 부담이 두 배가 된다.
- **영향:** R4 에 선체 레벨 보정 구현과 해시 테스트가 들어간다. MVP 는 전부 Lv1 이라 보정이 1 이고 M3~M7 에는 영향이 없다.

## ADR-020 해적·선형 레벨 Lv30 통일과 등급 배율 (2026-09-29, ADR-019 의 레벨 부분 대체)
- **배경:** 사용자 정정. ADR-019 의 등급별 최대 레벨(일반 15 ~ 전설 12)은 저등급이 전설을 수치로 넘게 만들어 전설의 의미를 없앤다. 의도는 “전설이 가장 강하고, 희귀·영웅은 능력에 따라 전략적 가치가 있다”였다.
- **결정:**
  - 모든 등급 Lv1~30. 피해·체력 = 데이터 기본값 × 등급 배율(일반 1.00 · 희귀 1.10 · 영웅 1.25 · 전설 1.45 · 신화 1.65) × 레벨 배율(1 + 4% × (Lv − 1)). 같은 레벨이면 항상 등급 순으로 강하다 (설계서 §4.4).
  - 희귀·영웅의 가치는 낮은 코스트·짧은 쿨다운·상황 효과로 둔다. 특성은 Lv10·20·30 (§4.3, §4.4).
  - 레벨업 비용을 Lv30 까지 구간 표로 다시 짰다(일반 기준 카드 3,827장·골드 625,950) (§13.7).
  - 선체 내구도는 선원 전력(등급 배율 × 레벨 배율의 평균)에 비례한다. 선형 업그레이드도 Lv1~30, 레벨당 HP +1%(최대 +29%)·건조 포인트 +1·탱크 +1, Lv10·20·30 보너스 (§3.5, §13.6).
  - 캠페인 적 레벨: 일반 1~12, 어려움 8~22, 지옥 18~30. 적 선형 1~8, 6~18, 15~30 (§6.1).
- **대안:** 전설이 더 높은 레벨에서 시작 — 사용자가 “레벨은 동일하게 30까지”로 정했다. 선원 보정에 레벨만 반영 — 전설 위주 덱의 피해를 배가 못 따라가 등급 배율까지 넣었다.
- **영향:** ADR-019 의 선원 레벨 보정 구조는 유지하되 식이 ‘전력’으로 바뀌었다. R4 범위가 같은 식으로 갱신됐다. MVP 는 전부 일반 Lv1 이라 보정이 1 이다.

## ADR-021 최대 레벨 50 (2026-09-29, ADR-020 의 레벨 폭 대체)
- **배경:** 사용자 정정. 해적 최대 레벨을 30에서 50으로 올리고, 내구도와 관련 수치를 모두 맞춘다.
- **결정:**
  - 해적 Lv1~50. 식은 ADR-020 그대로(등급 배율 × 레벨 배율 1 + 4% × (Lv − 1)). Lv50 은 일반 ×2.96 ~ 전설 ×4.29 · 신화 ×4.88. 특성은 Lv10·30·50 (설계서 §4.3, §4.4).
  - 레벨업 비용 5구간(10레벨씩). 일반 기준 카드 18,227장·골드 3,275,950. 카드는 등급 나눗셈(희귀 ÷2 ~ 신화 ÷20, 레벨마다 올림), 골드는 등급 무관 (§13.7).
  - 선형 업그레이드 Lv1~50: 레벨당 블록 HP +1%(최대 +49%)·탱크 +1, 건조 포인트는 짝수 레벨마다 +1(최대 +25), Lv15·30·50 보너스. 골드는 해적 레벨업 표와 같다. 기존 1.15^Lv 지수식은 Lv50 에서 한 레벨 47만 골드가 되어 버렸다 (§13.6).
  - 선체 내구도 예시와 재질별 최대치(참나무 511, 철판 959)를 다시 계산했다 (§3.5). 캠페인 적 해적 레벨 일반 1~20·어려움 15~38·지옥 32~50, 적 선형 1~14·10~30·25~50 (§6.1).
- **대안:** 건조 포인트를 레벨마다 +1 — 슬루프 60 이 109 가 되어 ‘같은 선형은 배치 실력으로 싸운다’가 흐려진다.
- **영향:** 골드·카드 수입(승리 골드, 상자 내용물, 상점 가격)이 설계서에 아직 수치로 없어 비용 곡선의 체감 속도는 검증하지 못했다. R4 에서 수입 표를 정하고 `sim` 이 아닌 경제 시뮬레이션(스프레드시트)으로 맞춘다.

## ADR-022 레벨업 카드 완화와 캠페인 전설 확률 상향 (2026-09-29, ADR-018·021 일부 대체)
- **배경:** 사용자 정정. 레벨업 카드가 너무 많아 초반에 지루해 이탈할 것이 걱정되고, 캠페인 전설 확률은 극악으로 두지 않는다(단, 많이 올리지는 않는다).

## ADR-024 새 기능은 계획서 마지막 단계 뒤 ‘추가 단계’로 붙인다 (2026-09-29)
- **배경:** 사용자 요청. 설계서가 계속 늘어나는데(캠페인 확장, 해적 획득, 레벨 50, 월간 출석 등) 새 기능을 기존 단계에 끼워 넣으면 진행 중이거나 끝난 로직과 섞여 같은 작업을 다시 하게 된다.

## ADR-025 흘수선 단위·구멍과 복구 규칙, M3 임시 수치 (2026-09-29)
- **배경:** M3(이동·연료·파도·침수·시간 판정)에 설계서에 없는 수치가 있었다. 흘수선 공식 (총무게 − 부력재) ÷ 선형 폭 은 샘플 슬루프(무게 50, 폭 12)가 4.2칸 잠겨 배 전체가 물에 들어간다.
- **결정 (사용자 결정, 설계서는 사용자 허락으로 에이전트가 직접 수정):**
  - 흘수선 높이(칸) = (총무게 − 부력재) ÷ (선형 폭 × 4). 판 시작 설계도로 정하고 전투 중에는 침수량만큼만 내려앉는다(§3.4).
  - 물이 새는 칸 = 흘수선 아래 ‘구멍’ 손상 단계 블록 + 부서진 칸(설계도에 있던 블록이 없어진 칸). 자기 턴이 끝날 때 계산한다. 부서진 칸은 되살릴 수 없고 수리는 ‘구멍’ 단계 블록만 되살린다(§2.5, §3.3, §4.2 #36).
  - MOVE 는 거리 ÷ 속도만큼 턴 시계를 쓴다. 이동 중에 들어온 다음 커맨드는 이동이 끝난 시각에 처리하고, 턴 제한 시간도 그 시각으로 판정한다.
  - 파도 위상은 커맨드 시각 `t`(턴 시작 기준, 비행 정지 포함)로 정한다. “놓는 순간을 고른다”(§2.5)를 결정론으로 만들려면 `t` 가 판정에 들어가야 한다. 설계서 §7.2 문구를 이에 맞게 고쳤다(ADR-027 때 사용자 요청). 턴제 PvP(§8.2)에서는 클라이언트가 보낸 `t` 를 믿는다(턴 시간 안이면 받아들임).
- **임시 수치 (설계서에 없음, `MatchRules` 값, 밸런스 단계에서 조정):** 파도 주기 4초, 파도 세기 0~3(기본 1, 1당 위아래 ±0.15칸·기울기 ±1°), 두 배의 파도는 반주기 어긋남, 파도 기울기와 침수 기울기는 발사 각도에 더함, 침수 기울기 = (앞 절반 − 뒤 절반 새는 칸) × 1°(최대 ±6°), 내려앉기 = 침수량 100% 에 2칸, 반쯤 잠김 = 흘수선이 칸 안을 지남, 폭풍 침수 1.5배는 턴 합계에 곱해 버림, 폭풍 타임 후퇴 한계 밖의 배는 폭풍 시작에 한계선으로 옮김.
- **대안:** 흘수선 공식을 글자 그대로 쓰고 테스트 배를 가볍게 짓는다 — 추천 설계도(§3.4)도 모두 잠겨 쓸 수 없다.
- **영향:** 계획서 M3 흘수선·침수 줄, M5 목수 공방·`repair` 문구를 고쳤다. 리플레이 형식 v4(규칙 수치 추가).

## ADR-027 물에 잠긴 선실은 쏠 수 없다, 이동 중 발사 입력 막기 (2026-09-29)
- **배경:** M3 코드 리뷰. 흘수선·내려앉기가 들어오면서 선실이 물 아래에 있을 수 있게 됐다(샘플 슬루프는 맨 아래 줄이 늘 잠기고, 3층 선실도 침수 약 73% 부터 잠긴다). 물속에서 쏘면 물보라 위치 계산이 틀어지고, 수직 속도가 중력과 같은 각도에서는 0 으로 나눠 판이 멈췄다.
- **결정 (사용자 결정):**
  - 선실 칸 중심이 잠긴 깊이(흘수선 + 내려앉기, 파도 제외) 이하면 그 해적은 쏠 수 없다(`SideState.canFire`). 파도가 잠깐 선실 중심을 물 아래로 내리면 해수면에서 쏜다. 물보라 계산은 발사점이 해수면 위일 때만 비율로 자른다.
  - 이동 중에 들어온 발사는 이동이 끝난 시각의 파도로 쏜다(ADR-025 그대로). 대신 M4 입력에서 이동하는 동안 당겨서 쏘기를 막아 보이는 파도와 어긋나지 않게 한다.
  - 리플레이 규칙 값 검사를 넓힌다: 폭풍 후퇴 당김 ≤ 20칸, 폭풍·파도·내려앉기·기울기 값 ≥ 0, 격침 비율 0~100.
  - 폭풍 타임에 한계선으로 옮겨진 배는 `move` 이벤트를 낸다.
- **대안:** 발사 위치를 해수면으로 끌어올린다 — 잠긴 선실이 약점이 되지 않고, 수중 계열(§2.1 수중 층)과 뜻이 섞인다.
- **영향:** 사용자 요청으로 설계서 §2.5 에 ‘잠긴 선실’ 문장을 넣고, §7.2 의 `t` 문구를 턴 시각·이동 시간·파도 위상 판정에 쓰도록 고쳤다. 계획서 M4 입력 항목에 한 줄을 더했다. 골든 해시는 바뀌지 않았다.

## ADR-028 해적보감(도감·해적 상세) 메뉴를 추가 단계 A2 로 (2026-09-29)
- **배경:** 사용자 요청. 해적을 카드로 모아 보고, 카드를 누르면 능력치와 정보를 보는 ‘해적보감’ 메뉴를 설계서와 계획서에 넣는다. 설계서에는 선원 화면 안의 ‘도감 탭’(40명 격자)과 ‘해적 상세’만 짧게 있었다.
- **결정 (설계서는 사용자 요청으로 에이전트가 직접 수정):**
  - 설계서 §13.9 해적보감을 새로 쓴다: 목록(카드 격자·수집 현황·필터·정렬·없는 해적 실루엣)과 상세(정보·능력치 레벨 미리보기·특성·소개·얻는 곳 탭, 레벨업·편성하기).
  - 해적 상세는 화면 하나로 합친다. 선원(§13.7)·항구(§13.2)에서 해적을 눌러도 같은 상세를 연다. §13.7 의 ‘도감 탭’은 해적보감 버튼으로 바꿨다.
  - 진입점은 하단 탭(5개 고정)이 아니라 항구 위쪽 아이콘이다(§13.1, §13.2).
  - 상세의 능력치는 전투에 넘기는 값과 같은 `pb_data` 계산으로 만든다. 화면이 따로 계산하면 수치가 어긋난다.
  - 해적 데이터에 `descKey`·`loreKey` 문자열 키를 더한다(§4.3).
  - 계획서: ADR-024 에 따라 12장 끝에 A2 로 붙이고, R1 의 ‘도감 탭’은 A2 로 옮겼다.
- **대안:** 하단 탭에 여섯 번째 탭 — 가로 모드 하단이 붐비고 ‘탭 3번이면 전투’ 흐름이 흐려진다. 선원 화면 안 탭으로 두기(기존) — 없는 해적과 얻는 곳을 보는 수집 메뉴로 찾기 어렵다.
- **영향:** M5 의 해적 데이터 스키마에는 아직 `descKey`·`loreKey` 를 넣지 않는다(A2 에서 추가). R4 에서 레벨업 UI 를 임시로 두면 A2 에서 상세 화면으로 합친다.

## ADR-030 계획서는 설계서를 따른다, 정합성 정리 (2026-09-30)
- **배경:** 사용자 요청으로 설계서와 계획서 전체를 대조했다. `check_doc_sync` 는 해시만 봐서 통과했지만, 계획서에 낡은 문구(첫 판 일반 4명), ADR 로 설계서와 다르게 적은 곳(M4 블록·바다·이동), 담당 단계가 없는 설계서 기능(시험 발사, 공유 코드, 덱 프리셋, 승리·패배 동작 등)이 있었다.
- **결정 (사용자 결정):**
  - 설계서가 유일한 기준이고 계획서는 설계서를 따른다(CLAUDE.md 절대 규칙 12). 설계서가 바뀌면 같은 커밋에서 계획서도 고친다. 설계서와 다르게 하려면 설계서 수정을 먼저 제안하고, 계획서·코드만 따로 바꾸지 않는다. ADR-008 을 강화한다.
  - 계획서 수정: M5 첫 출전은 시작 해적 2명(§4.6), MVP 에서 얻는 해적 6명과 적 전용 6명 구분, M7 해역 1 번호를 1-1~1-5(1-5 중간 보스)·1-12 보스로(§4.6, §5.4), M4 블록 손상은 코드로 그림·바다 측면 굴절 셰이더·이동은 누르는 동안 움직임(§2.2, §2.6, §10.2), M7 승리·패배 동작(§10.1), R2 시험 발사·공유 코드(§13.6), R3 지옥 후보 선택 최상·연패 보정 없음(§5.2, §6.1), R4 덱 프리셋·선실 힌트·`hull_*`/`growth_*`/`levelup_*`, 11장 해시(FNV-1a)·삼각 테이블(0.25°) 결정 표시.
  - ADR-029 의 “블록은 에셋 PNG 손상 타일”, “바다 셰이더 없음”, “뗄 때 MOVE 한 번” 은 계획서에서 설계서 문구로 되돌린다. M4 코드가 이미 ADR-029 방식이면 M4 할 일로 남기거나, 사용자가 설계서를 ADR-029 쪽으로 고친다.
  - `/doc-sync` 절차에 “계획서에 없는 설계서 기능의 단계 배정”, “ADR 로 벌어진 차이 되돌리기”, “설계서 내부 모순 보고”를 넣는다. 설계서만 바뀐 커밋은 이미 pre-commit·verify·CI 의 해시 검사가 막으므로 새 스크립트는 만들지 않는다.
- **대안:** ADR 결정이 설계서보다 우선 — 두 문서가 계속 어긋나고 어느 쪽이 맞는지 매번 물어야 한다. 내용 대조 스크립트 — 자연어 문서라 기계 대조가 어렵다.
- **영향:** 설계서 내부 모순(AI 생각 연출 시간, 실시간 표현, 팡 사거리, 크라키 침수, 모듈 비용·한도 없음 등)은 사용자에게 수정안으로 보고했다. 설계서는 바뀌지 않아 동기화 해시는 그대로다.


## ADR-031 해적 세트 효과를 설계서 §4.7 과 계획서 A3 로 (2026-09-30)
- **배경:** 사용자 요청으로 같은 편성에 특정 해적 조합이 있으면 공격·방어 보너스를 주는 세트 효과를 설계서에 넣었다. 최대 7명 출전이라 2세트·3세트 두 단계를 둔다.

- **영향:** 설계서 §4.3·§4.5·§4.7·§13.3·§13.4·§13.7·§13.9·§15.3 수정, 계획서 A3 추가·동기화 해시 갱신. 이미 끝난 단계와 현재 M4 코드에는 영향 없다.

## ADR-032 설계서 재대조(M0~M4)로 고친 판정 규칙 (2026-09-30)
- **배경:** 사용자 요청으로 바뀐 설계서를 기준으로 M0~M4 구현을 단계별로 다시 대조했다(감사 3건). 설계서와 어긋나거나 빠진 판정을 고친다.

  - 기울기(파도 + 침수, §2.5)를 발사 각도뿐 아니라 발사 위치와 충돌에도 쓴다. 회전 중심은 배 가운데 용골 바닥이고 앱도 같은 중심으로 돌려 그린다. 보이는 모습과 판정이 같다(절대 규칙 3).
  - 한 턴에 같은 해적은 두 번 쏠 수 없다(§2.3 “서로 다른 해적”)를 쿨다운과 따로 막는다(이번 턴에 쏜 슬롯, 해시 포함). 쿨다운은 0~2턴만 출전할 수 있다.
  - 블록이 부서지거나 무너진 발사는 부서지는 연출만큼 턴 타이머를 더 멈춘다(§2.3). 임시 값 600ms(`breakPauseMs`).
  - 이동 한계선 앞 0.5칸은 절반 속도로 시간이 더 든다(§2.6). 연료는 거리만큼(§2.7). `limitSlowZone` 500.
  - 탄도 세로 적분에 반 스텝 보정을 넣어 사거리가 §2.8 등급 거리에 가깝게 한다.
  - 결정론 검사에 앞자리 없는 실수 리터럴(`.5`)과 `hashCode` 를 더했다(§7.1).
  - 리플레이 형식 v5(새 규칙 값). 골든 해시 3424264738 → 1852174760, 골든 리플레이 다시 만듦.
- **임시 수치 추가:** 바람 세기 1 = 1/1000칸/틱²(`windAccel`, ADR-025 목록에 빠져 있던 값), 부서짐 정지 600ms.
- **사용자 확인이 필요한 설계서 문구 (제안만, 설계서는 그대로):** §7.2 예시의 `seedWind`·TAP `tick`, §3.4 흘수선 “− 부력재” 중복 해석과 건조 포인트 “상한/같다”, §3.1 선실 수(최대 vs 정확히), §10.2 손상 단계 경계값, §2.3·§4.7 헤엄 해적의 버티기와 턴 끝 침수 100%·펌프 순서, §2.2·§13.4 연료 게이지 위치, §14.1 전투 중 언어 변경.
- **영향:** M2·M3 테스트 수치와 골든을 다시 만들었다. 허수아비·테스트 조준 도우미도 시뮬레이션처럼 해수면에서 자르고 기울기를 반영한다.

## ADR-035 M5 게임 데이터 형식과 임시 수치 (2026-09-30)
- **배경:** M5 에서 해적·탄종 데이터를 `pb_data` 로 읽는다. 설계서 §4.3·§4.8 로 정해지지 않은 데이터 형식과 수치를 정한다. (ADR-034 는 다른 세션이 탄종 결정용으로 예약)
- **결정:**
  - 게임 데이터는 `app/assets/game/`(`ammo.json`, `pirates.json`)에 둔다. 에셋 가져오기 도구가 지우는 `app/assets/data/` 와 나눈다. `pb_data` 는 문자열을 받아 검증하고 `pb_sim` `PirateSpec` 을 만든다.
  - 데이터는 정수만 받는다(실수는 오류, §7.1). §4.3 예시의 `"gravity": 1.0` 은 쓰지 않는다(설계서 예시 수정을 제안할 것).
  - 사다리 칸은 정수 하나 또는 `[첫째, 둘째]`(설치탄: 지속 턴, 침수 0.1%p). 저격 배율·지원 배율은 %, 유도 선회력은 °/초.
  - 등급 배율(§4.4: 일반 1.00·희귀 1.10·영웅 1.25·전설 1.45·신화 1.65)은 `pb_data` 가 체력·블록 피해·해적 피해에 ‰ 로 곱한다. 레벨 배율은 R4(MVP Lv1).
  - 해적 JSON 의 탄종 고유 파라미터: `spreadDeg`(분열·연사), `repairCells`(지원탄), `delayed`(다중투하 다음 내 턴 투하). `pb_sim` 에서는 `spreadMdeg`·`ammoParam` 로 받는다.
  - 해적 id 는 `p<번호>_<이름>`, 글자 키는 `pirate_p<번호>_name/desc/lore` (ko·en ARB 같은 커밋).
- **임시 수치:** 12명의 체력·피해는 §4.3 계열 기준 표. 다중투하는 §4.3 표의 “발당 25/40” 을 한 발 피해로 쓴다(여러 발 합계 식과 겹치는 부분은 설계서 확인 필요). 폭발 반경은 데이터·특성과 관계없이 최대 2칸(§4.8)이라 반경 3칸 테스트 해적의 골든이 바뀌었다.
- **탄종 행동 모듈 (M5 1b):**
  - 분열탄: FIRE 뒤 계산을 미루고 다음 커맨드를 기다린다. 같은 슬롯의 `TAP` 이면 그 `tick` 에 조각으로 갈라지고, 다른 커맨드·턴 끝이면 갈라지지 않은 채 계산한다. `TAP` 의 `t` 는 FIRE 와 같게 낸다(턴 묶음 t 는 줄지 않는다). 조각은 지금 속도를 `spreadDeg` 부채꼴로 돌린다.
  - 턴 효과(설치탄 폭발·펠리 투하·강습 물기)는 `MatchState.effects` 에 걸린 순서대로 두고 해시에 넣는다. 걸린 진영이 아닌 “세는 진영” 의 턴 시작에 1 씩 줄어 0 이면 터지고, 곧바로 즉시 판정한다.
  - 거리 구분: 두 뱃머리 간격 16칸 이하 가까움, 36칸 이상 멂(§2.6). 직사 계열은 가까우면 피해 +20%, 멀면 −20% 에 각도 ±2° 흔들림(매치 난수). 관통 칸은 가까우면 +1, 멀면 −1(최소 1). 설치탄은 멀면 1턴 늦게 터진다.
  - 렌더용 경로 `MatchState.lastTraces` 는 해시에 넣지 않는다.
- **임시 수치 (1b, 손맛 체크포인트에서 조정):** 연사 간격 3틱, 물수제비 튕김 때 세로 속도 ×0.55·가로 ×0.85, 유도탄은 중력 없음·가장 가까운 배 위 상대 해적 쪽으로 선회, 다중투하(윙)는 꼭대기에서 가로 속도 0.5~1.5배로 흩음, 펠리 투하 높이 14칸·1칸 간격, 강습 물기는 해적만(블록 피해 0), 지원탄은 제 배에 내려올 때만 닿고 가까운 구멍 블록부터 최대 내구도 × 지원 배율%.

## ADR-036 밸런스 계산표 `docs/BALANCE.md` 를 기준 문서에 추가 (2026-09-30)

## ADR-037 밸런스 수치의 기준을 `docs/BALANCE.md` 로, 설계서·계획서는 참조 (2026-09-30)
- **배경:** 설계서에 규칙과 튜닝 수치가 섞여 있고 계획서도 같은 수치를 되풀이해, 수치 하나를 바꾸면 세 문서를 찾아 고쳐야 했다. 사용자 요청으로 밸런스 수치를 한 문서에 모은다.
- **결정 (사용자 결정):**
  - `docs/BALANCE.md` 가 **밸런스 수치의 기준**이다. A부는 설계서에서 옮긴 기준 수치(절 번호를 그대로 붙여 A2.3 ~ A13.7), B부는 A부에서 유도한 계산표다. ADR-036 의 “유도값만” 성격은 이 결정으로 바뀐다.
  - **옮긴 것:** 피해·체력·재질 내구도·무게·비용, 등급·레벨 배율, 코스트·한도·경험치, 해적별 쿨다운과 고유 효과 수치, 탄종 사다리와 균형 배율, 세트 효과 수치, 침수 %p, 연료, 사거리 칸 수, 이동 속도·거리 상성, 모듈 효과, 선체 보정, 폭풍 배율, AI 난이도 다이얼·턴 운영, 캠페인 모드 배율, 선형 업그레이드, 레벨업 비용, 보상 확률, 튜닝 목표.
  - **설계서에 남긴 것:** 규칙·공식·구조 상수(턴 25초·30턴·발사 2회·격자·선실 수·시작 간격·이동 구간·30Hz·×1000·궤적 30%), 화면·연출·서사, 수익화 가격·광고·보물상자·출석·KPI·네트워크 수치. 옮긴 자리에는 “수치: BALANCE.md A§n” 을 적는다.

  - `tool/check_doc_sync.dart` 가 설계서와 BALANCE.md 를 이어 붙여 FNV-1a 로 해시하고, 계획서 머리 표시를 `설계서 동기화:` → `기준 문서 동기화:` 로 바꾼다. ADR-008 의 마커·해시 정의는 이 결정으로 대체한다. `tool/test/check_doc_sync_test.dart` 를 추가했다.
  - 옮기면서 정리한 모순: 크라키 침수 “+10%p”(§4.6)는 “지속 턴 동안 턴 끝마다 사다리 값”, §3.5 “약 5배”는 “최대 ×4.88”, §14 en ARB 예시 “2-cell” 은 “1-cell”. 설계서 §5.1 에 “탭 탄종은 탭 시점 후보도 평가한다” 규칙을 넣고 값(3개)은 A5.1 에 둔다.
- **대안:** 설계서에 수치를 두고 BALANCE.md 는 계산표만 — 수치 변경 때 세 문서를 고쳐야 하는 문제가 그대로다. 숫자를 전부 옮기기 — 턴 시간·격자 같은 구조 상수까지 빠지면 설계서를 혼자 읽을 수 없다.
- **영향:** CLAUDE.md(기준 문서 표, 절차, 규칙 12, 명령 목록), `/doc-sync`·`/step-start`, docs/HARNESS.md, verify 4/7 단계 이름은 그대로. B부 생성 스크립트는 커밋하지 않는다(M6 선택 항목 `tool/balance_table.dart`).

## ADR-038 기능 모듈 배치·비용, 무게 연료 식, 화재 R1, 선형 건조 시간 (2026-09-30)
- **배경:** M5 3단계(기능 모듈·건조)를 시작하려는데 설계서에 모듈 비용·배치 방식·무게 연료 식이 없었다. 사용자가 답을 정하고 선형 건조 시간을 새로 요청했다.

  - 선형 업그레이드에 건조 시간(레벨이 높을수록 김), 업그레이드마다 보상형 광고 1회로 남은 시간 절반. 새 기능이라 계획서 12장 A4 (절대 규칙 11). (설계서 §13.6, §9)

- **해석:** 사용자의 ‘배 건조 레벨’을 선형 업그레이드 레벨(§13.6)로 보았다. 새 설계도를 저장하는 데는 시간이 걸리지 않는다.

## ADR-043 탄 비행 시간 1.5배(중력 36 → 16)와 카메라 착탄 추적 (2026-09-30)
- **배경:** 실기기에서 폭탄이 쏘자마자 떨어져 탄도가 보이지 않는다는 사용자 체감. 중력 36칸/초²(ADR-010 임시값)에서 긴 사거리 최대 힘 비행이 1.7초다.
- **결정 (사용자 결정):**
  - 사거리 표(A2.8)는 유지하고 중력과 탄속을 함께 낮춘다. 중력 16칸/초²(임시값), 탄속 = √(사거리 × 중력). 비행 시간은 √(36/16) = 1.5배(긴 사거리 2.5초). 탄 비행 중 턴 타이머는 멈추므로 턴 시간에는 영향이 없다.
  - 바람 가속은 중력에 대한 비율(단계당 2.5%)로 정의해 중력을 바꿔도 바람의 체감이 유지되게 한다.
  - 설계서 §2.1 카메라를 “탄을 따라 이동하며 화면 밖으로 내보내지 않고, 착탄·파괴 연출이 끝날 때까지 따라간 뒤 돌아온다. 상대 턴도 같다. 탄이 여럿이면 앞선 탄”으로 명시한다.
  - M3·M4 는 끝난 단계라 코드 반영은 계획서 A6 단계로 둔다(규칙 11).
- **대안:** 탄속만 낮추기 — 사거리가 줄어 A2.8 표 전체와 AI 사거리 판단이 흔들린다. 렌더 재생 속도만 늦추기 — 판정 시각(파도 위상·TAP 틱)과 연출이 어긋난다.
- **영향:** 설계서 §2.1·§2.3·§2.8, BALANCE.md A2.3·A2.8, 계획서 A6. 코드: 중력 상수·탄속 표·바람 단위·골든 해시(A6).

## ADR-044 격침 기준 20% → 30% (2026-09-30)
- **배경:** M6 `sim_runner` 에서 보통 AI 끼리 1만 판의 시간 판정이 30.2%(목표 25% 이하, BALANCE.md B10), 평균 24.7턴(목표 12~18)이었다. 격침(내구도)은 12.7% 로 적었다. AI 개선(사거리 밖이면 다가가기, 두 번째 발 겹침 피하기)으로 39% → 30% 까지 줄였고 남은 차이는 기준 수치 쪽이다.

## ADR-047 M7 마무리: 계획서와 달리 처리한 것 (2026-09-30)

## ADR-050 검토 지적 반영: 망사·다중투하 분배·화약고 ‘맞으면’·관통 두 번째 칸 50%·AI 정렬 (2026-10-01)
- **배경:** 다른 세션의 설계서 대비 구현 검토에서 pb_sim·pb_ai 몫 지적이 나왔다. 사용자는 1~4(망사, 다중투하 분배, AI 정렬, AI 테스트)를 바로 고치고, 5(화약고 시점)·6(핀)은 알아서 정하라고 했다.
- **결정:**
  - 망사(§3.2 ‘포탄 감속, 공중 공격 차단’): 공중 계열이 아닌 탄은 망사 칸을 지나가며 속도 50%, 망사는 탄의 블록 피해만큼 깎인다(칸마다 한 번). 공중 계열 탄은 망사에 멈춰 그 칸에 맞는다. 수치는 BALANCE.md A3.2 (임시값).
  - 다중투하: §4.8 여러 발 규칙대로 합계(기본 × 140%+)를 폭탄 수로 나눈다. A4.3 공중 행의 ‘발당 25/40’ 대신 기본 50/90 (일반 3개면 발당 23/42 로 거의 같다). 펠리 다음 턴 투하도 같다.
  - **화약고는 맞으면 터진다(5번, 제 판단):** 설계서 §3.3 이 화약고는 “맞으면 폭발”, 연료통은 “파괴되면” 피해로 일부러 나눠 적었다. 화약고가 더 위험한 고위험 고보상 모듈이라는 뜻으로 보고, 화약고 칸이 피해를 받으면(블록이 남아도) 한 번 터진다.
  - **관통탄 두 번째 칸부터 피해 50%(6번, 제 판단):** 측정에서 핀의 강함은 관통 2칸에서 왔다(관통 1칸이면 51%). 사다리를 1칸으로 내리면 일반 관통탄이 뚫지 못해 정체성이 사라지므로, 뚫기는 남기고 뒤 칸 피해를 줄인다. 설계서 §4.8 에 규칙 문장, 비율은 BALANCE.md A4.8.
  - AI 후보 정렬의 동점 순서: 점수 → 각도 → 힘 → 탭 틱.
- **영향:** 계획서 12장 A9, 골든 해시(망사·화약고·관통 규칙), 보통 AI 1만 판 재측정.

## ADR-051 설계서 재대조 2차: 보스 난이도 쉬움, 전투 중 언어 변경 불가, 문구 정리 (2026-10-01)

  - 해역 1 보스 1-5·1-12 의 AI 난이도는 다른 스테이지와 같은 쉬움이다(설계서 §6.1 ‘일반 모드 해역 1~2 쉬움’). 보스 차이는 덱·설계도·기믹(R3)으로 낸다.
  - 전투 중에는 언어를 바꾸지 않는다(§14.1). 일시정지 창에서 언어 선택을 뺐고 설정 화면에서만 고른다. ADR-029 의 개발용 저사양·자동 종료·상대 선택은 그대로 둔다.
  - 설계서·BALANCE.md 는 사용자 허락으로 에이전트가 직접 고쳤다(ADR-025 선례): §11.1 ‘AI 난이도 3단계’ → 4단계(ADR-040), §5.1 ‘각도·힘에 오차’ → 각도만(BALANCE.md A5.2 와 일치), §4.3 예시의 `gravity: 1.0` 제거(중력은 §2.8 전역 상수, 데이터는 정수만 ADR-035), §7.2 예시의 `seedWind` 제거(바람은 시드와 턴으로 유도, ADR-032 의 제안 반영), A6.1 별 턴 수는 양쪽 합산 턴 번호(구현 `app/lib/campaign/star_rules.dart`, ADR-047).
  - 계획서 체크박스(§2.2·A6·M4)와 11장 미정 사항을 실제에 맞췄고, 남은 앱·문서 지적은 A9 에 미체크 항목으로 넣었다.
- **대안:** 보스를 보통으로 두고 설계서 §6.1 을 고치는 것. 해역 1 은 첫 해역이라 설계서 의도(쉬움)를 따랐다.
- **영향:** `sea1.json`, `pause_menu.dart`, 테스트 2개, 계획서 동기화 해시. 골든 해시는 바뀌지 않는다.

## ADR-052 균열 피해: 폭발 바깥 몫을 지그재그 조각으로 분배, 찢긴 파괴 표현 (2026-10-01)
- **배경:** 사용자가 폭탄에 맞은 블록이 네모 칸 단위로 반듯하게 부서지는 것이 비현실적이라고 보고, 실제 폭발처럼 균열이 지그재그로 제멋대로 퍼지는 모양을 원했다. 렌더만 바꾸는 안과 판정까지 바꾸는 안을 제시했고 사용자는 **판정까지**를 택했다. 현재 `resolveImpact` 는 착탄 칸 100%, 반경 안 바깥 칸 전부에 균일 비율 피해를 주고 난수를 쓰지 않는다.
- **결정:**
  - **균열 피해(설계서 §4.8):** 반경 1칸 이상인 탄과 모듈 폭발(화약고·연료통)은 착탄 칸에 피해 전부를 주고, 바깥 몫을 균열 조각으로 나눠 매치 시드 xorshift32 로 착탄 칸에서 지그재그로 흩뿌린다. 조각은 블록 있는 칸으로만 가고 착탄 칸으로 돌아오지 않으며, 갈 곳이 없으면 사라진다(지금도 빈 칸에 간 바깥 피해는 버려지므로 균형이 같다). 같은 칸에 조각이 겹칠 수 있어 모양이 매번 다르다.
  - **기대 총피해 보존:** 조각 수 = 반경 안 바깥 칸 수(1칸 4개, 2칸 12개), 조각 피해 = 기본 피해 × 바깥 칸 비율. 착탄 칸 피해가 그대로라 재질 사다리(소나무 1·참나무 2·철판 4발)와 ADR-049 조정(바깥 40%)이 유지되고 B3 기대 피해 표는 바뀌지 않는다. 수치는 BALANCE.md A4.8 균형 규칙 값 표(임시값).
  - 선실 해적 피해·헤엄 해적은 원형 균일 그대로. 반경 0(단일 칸) 탄은 균열 없음.
  - **AI(절대 규칙 4):** 같은 커맨드를 내고, 후보 점수는 기대값(원형 균일 모델)으로 둔다. 미리보기는 dry 라 영향 없다.
  - **표현(설계서 §10.2):** 금은 칸 경계를 넘어 이어지고 부서진 칸 가장자리는 찢긴 모양으로 그린다. 칸 번호 시드 고정 패턴. 판정은 격자 그대로(§3, §7.1).
  - 설계서 §4.8·§10.2·§7.1 과 BALANCE.md A4.3·A4.8·B3 가정은 사용자 허락으로 에이전트가 직접 고쳤다(ADR-025·051 선례). A4.3 투척 행의 ‘바깥 칸 50%’ 는 ADR-049 뒤 남은 옛 값이어서 같이 고쳤다.
- **대안:** 렌더만 바꾸기(판정은 원형 균일 유지). 밸런스·골든·AI 영향이 없지만 피해 범위 자체는 네모 칸 조합이라 사용자가 택하지 않았다.
- **영향:** 계획서 12장 A10 신설(절대 규칙 11). 코드 반영은 A10: `resolveImpact` 호출처 전부에 rng 전달, 골든 100판 재생성, 보통 AI 1만 판 재측정, 앱 찢긴 가장자리 그리기. 남은 옛 값 BALANCE B1 표 ‘바깥 칸 50% 고정’ 과 B3 관통탄 일반 ‘2칸 × 50 = 100’(둘째 칸 50% 규칙이면 75)은 보고만 하고 고치지 않았다.

## ADR-053 개발용 테스트 대전: 해적 전원을 코스트 한도 없이 골라 AI 와 붙기 (2026-10-01)
- **배경:** 사용자가 실기기에서 해적을 몇 명밖에 못 써 봤다며 전체 해적(등급별)을 테스트할 수 있게 해 달라고 했다. 편성 화면은 12명을 다 보여 주지만 코스트 한도가 Lv1 고정 15라 조합이 막히고, 규칙에 안 맞는 덱은 전투에서 시작 덱으로 조용히 바뀐다. AI 와 바로 붙는 길은 캠페인(적 덱 고정)뿐이다.
- **결정:**
  - 항구 위쪽 바에 벌레 아이콘 → **테스트 대전** 화면(`app/lib/dev/`). 해적을 등급 구역별로 보여 주고 내 덱·상대 덱을 각 4명까지 고른다(상대 덱이 비면 시드로 무작위 4명). AI 난이도 4개 중 고르고 바로 전투한다. 양쪽 코스트 한도 99(사실상 없음), 상대 설계도는 기본 추천 설계도, 내 설계도는 대표 설계도.
  - 마지막으로 고른 덱은 `fleet` 상자 `test_deck_0`·`test_deck_1` 에 남긴다.
  - 디버그 빌드나 `--dart-define=DEV_TOOLS=true` 빌드에서만 보인다(`devTools`). 스토어 빌드에는 버튼이 없다.
  - 전투 규칙은 그대로 pb_sim. 앱은 덱·한도·난이도만 넘긴다(절대 규칙 3). 게임 기능이 아니라 설계서는 고치지 않는다.
- **대안:** 편성 화면 코스트 한도를 개발 빌드에서만 푸는 것. AI 상대 덱을 못 고르고 캠페인 적 덱에 묶여 택하지 않았다.
- **영향:** 계획서 A9 앱·문서 몫에 항목 추가. 출시 전에 ADR-029 핫시트와 함께 뺄지 다시 본다.


## ADR-054 조준 취소를 눈에 보이게: 당겼다가 되돌리면 '놓으면 취소' (2026-10-01)
- **배경:** 사용자가 해적을 끌어 조준하다가 마음이 바뀌어 다른 해적으로 바꿀 수 없다고 했다. 힘이 최소(`PullAim.minPower`) 아래면 놓아도 쏘지 않는 동작은 있었지만, 화면에 표시가 없어 알 수 없었다. 설계서 §2.2·§13.4 에도 조준 취소 규칙이 없다.
- **결정:**
  - 한 번 최소 힘 이상 당긴 뒤 누른 자리 가까이 되돌리면 궤적과 사거리 끝 표시를 숨기고 HUD 에 '놓으면 취소'(`aimCancel`)를 띄운다. 그대로 놓으면 쏘지 않고, 고른 해적은 남는다. 다른 카드나 배 위 해적을 바로 고를 수 있다.
  - 판정은 바꾸지 않는다. 앱 입력(`PullAim.isCancelling`)과 화면 상태(`aim.cancelling`)만 더한다(절대 규칙 3).
  - 사용자 결정으로 새 A 단계 없이 현재 브랜치에서 UX 버그 수정으로 처리한다.
- **대안:** 조준 중 다른 카드를 누르면 전환, 카드 줄에 놓으면 취소, 취소 버튼. 사용자가 되돌리기 표시만 골랐다.
- **영향:** 사용자 승인으로 설계서 §2.2·§13.4 에 취소 문구를 더하고, 계획서 M4 당겨서 쏘기 항목과 동기화 해시를 고쳤다.


## ADR-055 설계서 아트·등급 표현·에셋 키 동기화 (2026-10-01)
- **배경:** 아트 에셋 패키지 v0.21 과 ‘해적 캐릭터 단계별 개선’ 22단계까지의 디자인이 설계서 10장·13장·§4.3 문구보다 앞서 있었다. 설계서는 진갈색 외곽선·푸른 림라이트·볼터치, 무기 약 15개, 게임 크기 약 80px, 등급 색 테두리를 말했지만 실제 그림과 앱 데이터(`pirates.json`·`ammo.json`·`anims.json`)는 이미 다른 값을 쓴다. 사용자가 `/art-doc-sync` 로 고칠 절과 문안을 승인했다.
- **결정:**
  - 설계서를 사용자 승인으로 에이전트가 직접 고쳤다(ADR-025·051·052 선례). 승인된 절만 고쳤고 밸런스 수치와 BALANCE.md 는 바꾸지 않았다.
  - **§10 머리말:** 약 2.5등신, 남색 외곽선 한 가지(#14161c), 해 질 녘 주황 림라이트, 홍채·윗눈꺼풀이 있는 눈(볼터치 없음), 금 장식, 팀 색 값.
  - **§10.1:** 해적마다 고유 무기 1개(발사체 35 + 소형 폭탄 1 + 효과 아이콘 10)와 탄종 아이콘 13, 전투 크기 ‘키 약 1.5칸’, 부위 리그(캔버스 240×324, 기준점 발), 전투 외곽선, 고유 꼬리·명중 이름표.
  - **§10.2:** 블록은 SVG 타일(무늬 4가지, 칸 번호로 고정) 위에 손상 단계를 겹쳐 그린다. 젖은 타일·선실 타일. ADR-052 의 금·찢긴 가장자리 문장은 그대로다.
  - **§10.4(새)·§10.5(새):** 전투 연출(히트스톱·계열별 명중·붕괴·조준 표시·남은 턴 배지·탄종별 전달)과 등급 표현(카드 프레임 4종, 전투 등급 연출 표). 모두 렌더 전용이고 판정과 무관하다(절대 규칙 3).
  - **§4.3:** `render.species` 는 종족 이름이 아니라 아트 에셋 키다. 계열 키·탄종 키·해적 40명 id/species 표를 넣었다. 랍은 계열 키 `lob` 과 헷갈리지 않게 `lobster` 로 정한다.
  - **§13.4·§13.9·§14.4:** 카드는 등급 프레임과 탄종 칩, 예시 글꼴에 Black Han Sans 추가.
- **대안:** 설계서를 그대로 두고 그림을 설계서에 맞추는 것. 에셋이 이미 40명분 만들어졌고 앱 데이터가 그 키를 쓰고 있어 택하지 않았다.
- **영향:** 계획서 M4·M5·R6·운영·A2 문구를 설계서에 맞추고 12장 끝에 A11 을 새로 넣었다(절대 규칙 11). 코드는 바꾸지 않았다. 앱에 아직 없는 것(등급 프레임, 전투 등급 연출, 히트스톱 등 §10.4, 무늬 4번째·선실 타일, 글꼴 2종)은 A11 에서 한다. 젖은 타일·철판 무늬 변형은 에셋에 없고, 랍 에셋 폴더 이름은 `lob` 이라 디자인 쪽에서 맞춰야 한다. ADR-014·026 의 아트 방향(플랫 2D 벡터, 에셋 패키지)은 그대로이고 스타일 세부 규칙만 바뀐다.

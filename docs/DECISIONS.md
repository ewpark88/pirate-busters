# 결정 기록 (ADR)

새 패키지 추가, 규칙 변경, 계획 변경은 여기에 남긴다. 형식: 배경 → 결정 → 대안 → 영향.

## ADR-001 모노레포는 Dart pub workspace (2026-09-29)
- **배경:** 설계서 §7.3 의 패키지 구조(`pb_sim`, `pb_ai`, `pb_data`, `app`, `sim_runner`)를 한 저장소에서 관리해야 한다.
- **결정:** Dart 3.12 에 내장된 pub workspace 를 쓴다. 루트 `pubspec.yaml` 이 멤버를 나열하고, lock 파일은 루트에 하나만 둔다.
- **대안:** melos. 설치할 도구가 하나 늘고, 지금 규모에서는 workspace 로 충분하다.
- **영향:** `flutter pub get` 은 루트에서 한 번만 실행한다. 테스트는 패키지 디렉터리에서 `dart test` 로 돌린다(`tool/verify.sh`).

## ADR-002 패키지 의존 방향: pb_sim 이 중심 (2026-09-29)
- **결정:** `pb_sim` 은 워크스페이스 패키지에 의존하지 않는다. `pb_ai`, `pb_data` 는 `pb_sim` 에만 의존한다. `app`, `sim_runner` 가 모두를 조립한다. `tool/architecture/rules.dart` 가 검사한다.
- **이유:** 전투 엔진이 도메인이고, 데이터(JSON)는 어댑터다(mozzi `domain ← data` 와 같은 방향). `pb_data` 가 JSON 을 `pb_sim` 의 정수 정의로 바꾸므로 `pb_sim` 은 JSON 을 모른다.
- **영향:** 개발 계획서 §2.1 의 의존 방향 표기를 이 결정에 맞게 고쳤다.

## ADR-003 결정론을 자동으로 검사 (2026-09-29)
- **결정:** `pb_sim`, `pb_ai` 의 lib 에서 `dart:math`, `dart:async` import, `double`/`num`/`toDouble`/`Random`/`DateTime`/`Stopwatch`/`identityHashCode` 식별자, 실수 리터럴, `/` 연산자를 금지한다. 주석과 문자열은 검사하지 않는다.
- **이유:** 설계서 §7.1, §12 “시뮬레이션 패키지에서 double 사용을 린트로 금지”. Dart 의 `int / int` 는 `double` 을 만들기 때문에 `/` 도 막는다(`~/` 사용).
- **대안:** `custom_lint` 플러그인. 의존성과 설정이 늘어나므로, mozzi 처럼 스크립트 검사로 시작한다.
- **한계:** `Map` 순회 순서 같은 규칙은 자동으로 못 잡는다 → 리뷰와 골든 해시 테스트로 잡는다.

## ADR-004 mozzi 코드는 복사 후 수정 (2026-09-29)
- **결정:** 공용 패키지로 분리하지 않고 필요한 파일을 복사해 고친다. 목록은 `docs/MOZZI_REUSE.md`.
- **이유:** mozzi 코드는 `double` 기반이고 GDD 수치와 엮여 있어 그대로 공유할 수 없다. 두 게임 모두 진행 중이라 공용 패키지의 API 를 고정하기 이르다.
- **대안:** 공용 패키지 `mozzi_kit`. 두 게임에서 안정되면(정식 출시 이후) 다시 검토한다.

## ADR-005 로컬 저장소는 Hive CE (2026-09-29)
- **결정:** 설계서 §7.4 의 “Isar 또는 Hive” 중 `hive_ce` 를 쓴다. M7 에서 추가한다.
- **이유:** mozzi 와 같은 패키지다. Isar 는 원 저장소 유지보수가 멈췄다.

## ADR-006 Android 먼저 (2026-09-29)
- **결정:** MVP 와 정식 출시는 Android 로 한다. iOS 는 출시 이후 검토한다.
- **이유:** 비공개 테스트가 Play 기준이고(설계서 §11.2), 계정은 Google Play Games Services(§7.4)다. mozzi 와 같은 방침이다.
- **영향:** `app` 은 android 플랫폼만 생성했다. applicationId 는 `com.repo.pirate_busters`.

## ADR-007 리플레이·커맨드·설계도 직렬화는 pb_sim 이 갖는다 (2026-09-29)
- **배경:** 개발 계획서 M1 은 `pb_sim` 에 리플레이 JSON 저장·읽기를 둔다. ADR-002 는 “`pb_sim` 은 JSON 을 모른다”고 적었다.
- **결정:** 엔진 자체의 산출물(커맨드, 설계도, 리플레이)은 `pb_sim` 이 `toJson()`/`fromJson(Map)` 을 갖는다. `dart:convert` 는 쓰지 않고 문자열 변환은 호출하는 쪽이 한다. 해적·블록·스테이지 같은 **콘텐츠 데이터** JSON 은 계속 `pb_data` 가 읽어 `pb_sim` 정의로 바꾼다.
- **이유:** 리플레이는 PvP·버그 재현·부정 검사에서 엔진과 한 몸으로 움직인다(설계서 §7.2). 형식 버전을 엔진과 같이 올려야 한다.
- **대안:** 코덱을 `pb_data` 에 둔다. M1 이 `pb_data` 까지 건드리고 형식과 엔진이 멀어진다.
- **영향:** ADR-002 의 “JSON 을 모른다”는 콘텐츠 데이터에 한정한다. 리플레이 JSON 에는 `version` 필드를 둔다(현재 1).

## ADR-008 설계서가 바뀌면 개발 계획서를 같이 고친다 (2026-09-29)
- **배경:** 게임 설계서는 계속 갱신된다. 개발 계획서는 설계서를 작업 단위로 쪼갠 문서라, 설계서만 바뀌면 에이전트가 낡은 계획대로 작업하게 된다.
- **결정:** 계획서 머리에 `설계서 동기화: <해시>` 를 둔다. 해시는 설계서 본문(LF 정규화)의 FNV-1a 32비트 값이다. `tool/check_doc_sync.dart` 가 비교하고 `verify` 4/5 단계에서 돌린다. 값이 다르면 계획서에 변경을 반영한 뒤에만 해시를 갱신한다(절차: CLAUDE.md).
- **대안:** 규칙 문장만 둔다. 설계서를 사용자가 직접 고치므로 에이전트가 변경을 놓치기 쉽다. git 커밋 해시 비교는 커밋 전 수정과 리베이스에 약하다.
- **영향:** 설계서만 고친 상태에서는 verify 가 실패한다. `/step-start` 는 이 검사부터 한다.

## ADR-009 설계서 배 이동(§2.6, §5.5) 을 계획에 넣는다 (2026-09-29)
- **배경:** 설계서에 배 좌우 이동(전진·후퇴 한계, `MOVE` 커맨드, 거리 상성, AI 회피)이 추가됐고 MVP 범위(§11.1)에도 들어갔다.
- **결정:** 시뮬 쪽 이동과 `MOVE` 커맨드는 M2 에 넣는다. 탄도·충돌을 처음 만들 때 배가 움직이는 것을 전제로 해야 나중에 고치지 않는다. 침수 감속·폭풍 한계는 M3, 버튼·한계선 표시는 M4, 속도 요인·거리 상성은 M5, AI 이동은 M6, 나머지 선형 속도는 R2, 지옥 회피는 R3 에 둔다.
- **대안:** 이동 전체를 M5(선형·건조와 같이)로 미룬다. M2 의 탄도·충돌을 고정 위치로 만들었다가 다시 고쳐야 한다.
- **영향:** 완료된 M1 의 `Command` 에 `MOVE` 가 없다 → M2 에서 추가하고 리플레이 형식을 확인한다. M2 작업량이 늘어 MVP 일정(6주)이 밀릴 수 있다.

## ADR-010 M2 전투 판정 구조와 임시 수치 (2026-09-29)
- **배경:** M2(탄도·타격·붕괴)를 만들려면 해적이 탈 자리, 해적 수치, 좌표계가 필요하다. 설계서에 없는 수치도 있다.
- **결정:**
  - 선실 모듈만 M5 에서 M2 로 당긴다. 설계도에 `cabins: [[x, y], …]` 를 두고, 입력 순서가 슬롯 번호다. 개수는 선형의 선실 수와 같아야 하고 블록 위에 있어야 한다.
  - 해적은 선실 칸 **안**에 있다. 선실 블록이 방패라 직격은 블록이 받고, 해적은 폭발 반경 피해만 받는다. 선실 블록이 부서지거나 무너지면 최대 HP 20% 피해를 입고 바다로 떨어진다. 선실이 없는 채로 돌아온 해적은 드러나 있어 직격에 맞는다(사용자 결정).
  - 거리 24칸(16~32)은 **뱃머리 사이 간격**이다(사용자 결정). 설계도는 뱃머리가 +x 인 로컬 격자로 짓고 오른쪽 진영은 좌우를 뒤집는다. FIRE 각도도 “상대 쪽 수평 = 0°”로 진영마다 뒤집는다.
  - 해적 수치는 M5 `pb_data` 전까지 `PirateSpec`/`PirateCatalog` 으로 넘긴다. 리플레이는 덱 id 만 담고 재생할 때 카탈로그를 받는다.
  - 리플레이 형식 v2(선실·바람·MOVE). v1 은 읽지 않는다(배포된 리플레이가 없다).
  - 교대 대기열은 선형과 무관하게 “덱에서 선실 수를 넘는 해적”으로 만든다.
- **임시 수치 (설계서에 없음, 밸런스 단계에서 조정):** 중력 36칸/초², 최대 탄속 40칸/초(45° 로 30칸이면 1.3초), 폭발 가장자리 50% 피해, 손상 단계 2/3·1/3 경계, 헤엄치는 해적 위치는 뱃머리 1칸 앞 해수면이고 폭발·물보라 1칸(또는 폭발 반경) 안이면 즉사, 교대 해적은 재장전부터 시작, 탄은 쏜 진영 배에 닿지 않음, 바다에 떨어진 탄은 블록을 다치게 하지 않음, 해수면 = 용골 바닥(흘수선은 M3).
- **대안:** 선실 없이 해적을 추상 슬롯으로만 둔다. 선실 파괴·낙하·헤엄 카운터 플레이(설계서 §2.3)를 M2 에서 검증할 수 없다.
- **영향:** 골든 해시가 바뀌었다(2447913407 → 190143163). 설계서 §3.1 “슬롯이 6개 이상이면 … 교대 대기열” 과 계획서 M2 “교대 대기열” 의 범위가 어긋난다 → 사용자 확인 필요.

## ADR-011 턴제 전환에 맞춰 계획을 다시 짠다 (2026-09-29)
- **배경:** 설계서가 실시간 포격전에서 턴제(30초 턴, 턴당 이동·발사 2회, 8분 경기 시계, 쿨다운 턴, 연료, 누적 침수량, 시간 판정)로 바뀌었다. 한국어·영어 동시 지원(§14)과 화면 설계(§13)도 추가됐다.
- **결정:**
  - M2 = 턴 루프·탄도·타격·붕괴, M3 = 이동·연료·파도·침수·시간 판정, M4 = 렌더·입력·턴 UI·다국어 기반, M5 = 해적 쿨다운·모듈 9종(연료통)·건조·선원 편성, M6 = AI 턴 운영, M7 = 캠페인·화면(§13)·튜토리얼 3판·출시 준비. 설계서 §11.1 의 주차 계획은 이 순서로 옮겼다(계획서 §4).
  - 다국어 규칙을 CLAUDE.md 절대 규칙 10 으로 넣는다(설계서 §14.5 가 요구). ARB 키 검사는 M4 에서 verify·CI 에 붙인다.
  - ADR-009 의 이동 배치(실시간 `MOVE dir`, 관성, 회피)와 ADR-010 의 일부(뱃머리 간격 24칸, 헤엄 4초, 재장전 틱)는 이 결정으로 대체한다.
- **작업 중인 M2 코드(`feat/M2-ballistics`, 커밋 전)에 주는 영향:**
  - 그대로 쓴다: 월드 좌표·`ShipFrame`, 포물선 탄도, DDA 충돌, 블록 피해·손상 단계, 원형 폭발, 지지 구조 BFS, 선실·`Crew` 뼈대, `PirateSpec`/`PirateCatalog`, 이벤트 스트림.
  - 다시 짠다: `Command`(틱 → 턴 묶음, `END_TURN`, `MOVE(dx)`), `Match.step`(턴 루프·타이머·경기 시계), 재장전 틱 → 쿨다운 턴, 헤엄 4초 → 다음 내 턴 시작 복귀, 파괴 0% → 격침 20% 미만, 턴당 바람, 리플레이(턴 묶음 목록).
  - M3 로 옮긴다: `ShipMotion`(관성 이동 → 연료·dx 이동), 시작 간격 24 → 16칸.
- **대안:** 실시간 M2 를 먼저 끝내고 나중에 턴제로 고친다. 커맨드·리플레이·해시 형식을 두 번 바꾸게 된다.
- **영향:** MVP 범위가 늘어 6주 일정이 밀릴 수 있다. 설계서에서 확인할 것 4가지를 계획서 11장에 적었다(경기 시계와 결정론, AI 생각 연출 시간, 교대 대기열 범위, 실시간 표현 잔재).

## ADR-012 교대 대기열 → 출전 코스트, 8분 시계 → 30턴 제한 (2026-09-29)
- **배경:** 사용자 기획 변경. 교대 대기열은 필요 없고, 출전은 최대 7명, 경기 길이는 시간 대신 턴 수로 제한한다.
- **결정 (설계서에 반영, 사용자 지시로 직접 수정):**
  - 해적 등급을 노멀·매직·레어·전설·신화 5단계로 바꾸고 코스트를 3·4·5·6·8 로 둔다. 기존 등급은 일반→노멀, 희귀→매직, 영웅→레어, 전설→전설로 옮겼고 신화는 시즌 해적부터 쓴다.
  - 출전 코스트 한도는 **선형 레벨**에 따라 오른다(Lv1 15, 레벨당 +2, Lv10 33). 인원은 선실 수 이하, 최대 7명. 교대 대기열은 없다(설계서 §3.1, §4.5).
  - 한 판은 양쪽 합쳐 30턴(각자 15턴), 턴 시간 25초. 폭풍 타임은 27~30턴(폭풍 중 턴 시간 20초), AI 시간 판정 모드는 22턴부터.
  - 갤리온 Lv10 특성 “선실 +1”은 7명 상한과 맞지 않아 “선체 블록 HP +10%”로 바꿨다(예시 값).
- **이유:** 턴 수 제한은 실제 시간이 판정에 들어가지 않아 결정론 문제(계획서 11장)가 사라진다. 코스트는 강한 해적을 몇 명 태울지를 편성의 선택으로 만든다.
- **대안:** 코스트 한도를 선장(플레이어) 레벨에 묶는다. 선실 배치는 배의 속성이라 선형 레벨을 골랐다.
- **영향:** M2 에 출전 코스트 검증이 들어가고 교대 대기열 코드는 지운다. 레벨업 카드 표의 등급 배수도 새 이름(매직 ÷2, 레어 ÷5, 전설 ÷10, 신화 ÷20)으로 바꿨다.

## ADR-013 등급 이름 유지, 출전 코스트 한도는 플레이어 레벨 (2026-09-29)
- **배경:** ADR-012 의 등급 이름(노멀·매직·레어)과 선형 레벨 기준 한도를 사용자가 되돌렸다.
- **결정:** 등급은 일반·희귀·영웅·전설·신화(코스트 3·4·5·6·8). 출전 코스트 한도는 **플레이어 레벨**(1~20)에 따라 Lv1 15, 레벨마다 +1(Lv20 34). 플레이어 경험치는 승리 30·패배/무승부 10·캠페인 첫 클리어 +20, 다음 레벨 필요량 100 × Lv (예시 값, Remote Config). 선형 업그레이드는 한도와 관계없다. 최대 30턴·턴 25초는 언제든 바뀔 수 있는 값으로 두고 설정값으로 구현한다.

## ADR-017 캠페인 확장: 해역당 12스테이지·중간 보스·3모드 (2026-09-29)
- **배경:** 사용자 요청. 6해역 × (5스테이지 + 보스) = 36판은 정식 출시 캠페인으로 너무 작았다.

  - 화면은 같은 해역 배경에 조명·팔레트만 바꿔 낮 → 해질녘 → 폭풍 밤으로 어두워지고, 적 돛·깃발을 모드 색으로 바꾼다 (§10.2). 새 그림은 없다.

- **영향:** R3 가 ‘해역 2~6’ 에서 ‘캠페인 완성’ 으로 커졌다(스테이지 72, 중간 보스 6, 모드 3). 대사 ARB 키가 크게 늘어난다. `sim_runner` 로 모드별 난이도 곡선을 확인해야 한다. M3~M7 코드에는 영향이 없다.

## ADR-018 시작 해적 2명과 캠페인 해적 보상 (2026-09-29)
- **배경:** 사용자 요청. 설계서에 시작 해적이 없었고(“첫 판은 일반 4명”만 있음), 캠페인에서 해적을 얻는 규칙이 “세력 종족 카드”뿐이었다.
- **결정:**
  - 시작 해적은 옥토(투척)·톡(지원) 2명. 해역 1 확정 보상으로 수리·폴리·팡·샤키를 주어 덱 4칸과 계열을 채운다 (설계서 §4.6).
  - 해역 2~6 보스는 세력 종족의 일반·희귀 1명을 확정으로 준다(본즈·윙·핑구·젤리, §15.3).
  - 스테이지 3·7·10·중간 보스·보스 첫 클리어에 확률 보상. 초반 일반·희귀, 뒤로 갈수록 영웅, 전설은 0~1.5% (`reward_*`).
  - 성능 기준 최강 10명(램프·만타·모비·오르카·크라키·볼케·킹·쿡·모레이·라이언)은 캠페인 보상에서 빼고 상자·상점에서만 나온다(`campaignReward: false`). 등급이 아니라 효과로 골랐다.

## ADR-019 등급별 최대 레벨과 선원 레벨에 비례하는 선체 내구도 (2026-09-29)
- **배경:** 사용자 요청. 해적 레벨은 모든 등급이 Lv1~10(+8%/Lv, 최대 +72%)이었는데, 배 내구도는 선형 업그레이드 +3%/Lv(최대 +27%)뿐이었다. 레벨이 오를수록 피해가 내구도를 크게 앞질러 후반 전투가 몇 발에 끝나는 구조였다.
- **결정:**
  - 해적 최대 레벨을 등급별로 둔다: 일반 15 · 희귀 14 · 영웅 13 · 전설·신화 12. 레벨당 피해·체력 +6%. 높은 등급은 효과, 낮은 등급은 레벨 상한으로 강해진다 (설계서 §4.4). 레벨업 비용 표를 Lv15 까지 늘렸다 (§13.7).
  - 블록 내구도 = 재질 × 선원 레벨 보정(1 + 6% × (출전 해적 평균 레벨 − 1)) × 선형 업그레이드 보정(+3%/Lv). 해적 피해와 같은 곡선이라 같은 레벨끼리는 판 길이가 비슷하다 (§3.5).
  - 보정은 매치 시작 때 ‰ 정수로 pb_sim 에 넘긴다. 격침·동률 판정은 내구도 비율로 한다.
  - 캠페인 적 해적 레벨을 새 상한에 맞추고(일반 1~6, 어려움 4~10, 지옥 8~15) 적 선형 레벨을 더했다 (§6.1).
  - 데이터의 `growth` 에서 실수 성장률·`maxLv` 를 빼고 특성 키만 둔다 (§4.3).
- **대안:** 모든 등급 같은 최대 레벨 — 사용자가 원한 “높은 레벨의 희귀·영웅이 전설보다 강할 수 있음”이 약해진다. 선형 업그레이드만으로 내구도를 키움 — 해적만 키운 플레이어의 배가 녹고, 업그레이드 부담이 두 배가 된다.
- **영향:** R4 에 선체 레벨 보정 구현과 해시 테스트가 들어간다. MVP 는 전부 Lv1 이라 보정이 1 이고 M3~M7 에는 영향이 없다.

## ADR-020 해적·선형 레벨 Lv30 통일과 등급 배율 (2026-09-29, ADR-019 의 레벨 부분 대체)
- **배경:** 사용자 정정. ADR-019 의 등급별 최대 레벨(일반 15 ~ 전설 12)은 저등급이 전설을 수치로 넘게 만들어 전설의 의미를 없앤다. 의도는 “전설이 가장 강하고, 희귀·영웅은 능력에 따라 전략적 가치가 있다”였다.
- **결정:**
  - 모든 등급 Lv1~30. 피해·체력 = 데이터 기본값 × 등급 배율(일반 1.00 · 희귀 1.10 · 영웅 1.25 · 전설 1.45 · 신화 1.65) × 레벨 배율(1 + 4% × (Lv − 1)). 같은 레벨이면 항상 등급 순으로 강하다 (설계서 §4.4).
  - 희귀·영웅의 가치는 낮은 코스트·짧은 쿨다운·상황 효과로 둔다. 특성은 Lv10·20·30 (§4.3, §4.4).
  - 레벨업 비용을 Lv30 까지 구간 표로 다시 짰다(일반 기준 카드 3,827장·골드 625,950) (§13.7).
  - 선체 내구도는 선원 전력(등급 배율 × 레벨 배율의 평균)에 비례한다. 선형 업그레이드도 Lv1~30, 레벨당 HP +1%(최대 +29%)·건조 포인트 +1·탱크 +1, Lv10·20·30 보너스 (§3.5, §13.6).
  - 캠페인 적 레벨: 일반 1~12, 어려움 8~22, 지옥 18~30. 적 선형 1~8, 6~18, 15~30 (§6.1).
- **대안:** 전설이 더 높은 레벨에서 시작 — 사용자가 “레벨은 동일하게 30까지”로 정했다. 선원 보정에 레벨만 반영 — 전설 위주 덱의 피해를 배가 못 따라가 등급 배율까지 넣었다.
- **영향:** ADR-019 의 선원 레벨 보정 구조는 유지하되 식이 ‘전력’으로 바뀌었다. R4 범위가 같은 식으로 갱신됐다. MVP 는 전부 일반 Lv1 이라 보정이 1 이다.

## ADR-021 최대 레벨 50 (2026-09-29, ADR-020 의 레벨 폭 대체)
- **배경:** 사용자 정정. 해적 최대 레벨을 30에서 50으로 올리고, 내구도와 관련 수치를 모두 맞춘다.
- **결정:**
  - 해적 Lv1~50. 식은 ADR-020 그대로(등급 배율 × 레벨 배율 1 + 4% × (Lv − 1)). Lv50 은 일반 ×2.96 ~ 전설 ×4.29 · 신화 ×4.88. 특성은 Lv10·30·50 (설계서 §4.3, §4.4).
  - 레벨업 비용 5구간(10레벨씩). 일반 기준 카드 18,227장·골드 3,275,950. 카드는 등급 나눗셈(희귀 ÷2 ~ 신화 ÷20, 레벨마다 올림), 골드는 등급 무관 (§13.7).
  - 선형 업그레이드 Lv1~50: 레벨당 블록 HP +1%(최대 +49%)·탱크 +1, 건조 포인트는 짝수 레벨마다 +1(최대 +25), Lv15·30·50 보너스. 골드는 해적 레벨업 표와 같다. 기존 1.15^Lv 지수식은 Lv50 에서 한 레벨 47만 골드가 되어 버렸다 (§13.6).
  - 선체 내구도 예시와 재질별 최대치(참나무 511, 철판 959)를 다시 계산했다 (§3.5). 캠페인 적 해적 레벨 일반 1~20·어려움 15~38·지옥 32~50, 적 선형 1~14·10~30·25~50 (§6.1).
- **대안:** 건조 포인트를 레벨마다 +1 — 슬루프 60 이 109 가 되어 ‘같은 선형은 배치 실력으로 싸운다’가 흐려진다.
- **영향:** 골드·카드 수입(승리 골드, 상자 내용물, 상점 가격)이 설계서에 아직 수치로 없어 비용 곡선의 체감 속도는 검증하지 못했다. R4 에서 수입 표를 정하고 `sim` 이 아닌 경제 시뮬레이션(스프레드시트)으로 맞춘다.

## ADR-022 레벨업 카드 완화와 캠페인 전설 확률 상향 (2026-09-29, ADR-018·021 일부 대체)
- **배경:** 사용자 정정. 레벨업 카드가 너무 많아 초반에 지루해 이탈할 것이 걱정되고, 캠페인 전설 확률은 극악으로 두지 않는다(단, 많이 올리지는 않는다).
- **결정:**
  - 레벨업 카드(일반 기준)를 약 1/10 로 줄였다: Lv1→10 은 레벨마다 1~5장(합 25), Lv1→50 합 1,750장. 등급 나눗셈도 완화했다: 희귀 ÷2 · 영웅 ÷3 · 전설 ÷5 · 신화 ÷8 (전설 Lv50 까지 366장). 골드 표는 그대로다 (설계서 §13.7).
  - 캠페인 확률 보상의 전설을 1~5% 로 올렸다: 일반 모드 해역 1~2 1%, 3~4 2%, 5~6 3%, 어려움 4%, 지옥 5% (§4.6). 최강 10명 제외 규칙은 그대로라 캠페인 전설은 볼트·데비만 나온다.
- **대안:** 카드는 그대로 두고 카드 수입을 늘림 — 수입 수치가 아직 없어 비용 쪽을 먼저 낮췄다.
- **영향:** 뒤 레벨의 진행 속도는 카드보다 골드가 정한다. 골드·카드 수입 표는 R4 에서 정해 경제 시뮬레이션으로 확인한다.

## ADR-023 최강 10명도 캠페인 확률 보상에 낮은 확률로 포함 (2026-09-29, ADR-018 일부 대체)

## ADR-024 새 기능은 계획서 마지막 단계 뒤 ‘추가 단계’로 붙인다 (2026-09-29)

## ADR-025 흘수선 단위·구멍과 복구 규칙, M3 임시 수치 (2026-09-29)
- **배경:** M3(이동·연료·파도·침수·시간 판정)에 설계서에 없는 수치가 있었다. 흘수선 공식 (총무게 − 부력재) ÷ 선형 폭 은 샘플 슬루프(무게 50, 폭 12)가 4.2칸 잠겨 배 전체가 물에 들어간다.
- **결정 (사용자 결정, 설계서는 사용자 허락으로 에이전트가 직접 수정):**
  - 흘수선 높이(칸) = (총무게 − 부력재) ÷ (선형 폭 × 4). 판 시작 설계도로 정하고 전투 중에는 침수량만큼만 내려앉는다(§3.4).
  - 물이 새는 칸 = 흘수선 아래 ‘구멍’ 손상 단계 블록 + 부서진 칸(설계도에 있던 블록이 없어진 칸). 자기 턴이 끝날 때 계산한다. 부서진 칸은 되살릴 수 없고 수리는 ‘구멍’ 단계 블록만 되살린다(§2.5, §3.3, §4.2 #36).
  - MOVE 는 거리 ÷ 속도만큼 턴 시계를 쓴다. 이동 중에 들어온 다음 커맨드는 이동이 끝난 시각에 처리하고, 턴 제한 시간도 그 시각으로 판정한다.
  - 파도 위상은 커맨드 시각 `t`(턴 시작 기준, 비행 정지 포함)로 정한다. “놓는 순간을 고른다”(§2.5)를 결정론으로 만들려면 `t` 가 판정에 들어가야 한다. 설계서 §7.2 문구를 이에 맞게 고쳤다(ADR-027 때 사용자 요청). 턴제 PvP(§8.2)에서는 클라이언트가 보낸 `t` 를 믿는다(턴 시간 안이면 받아들임).
- **임시 수치 (설계서에 없음, `MatchRules` 값, 밸런스 단계에서 조정):** 파도 주기 4초, 파도 세기 0~3(기본 1, 1당 위아래 ±0.15칸·기울기 ±1°), 두 배의 파도는 반주기 어긋남, 파도 기울기와 침수 기울기는 발사 각도에 더함, 침수 기울기 = (앞 절반 − 뒤 절반 새는 칸) × 1°(최대 ±6°), 내려앉기 = 침수량 100% 에 2칸, 반쯤 잠김 = 흘수선이 칸 안을 지남, 폭풍 침수 1.5배는 턴 합계에 곱해 버림, 폭풍 타임 후퇴 한계 밖의 배는 폭풍 시작에 한계선으로 옮김.
- **대안:** 흘수선 공식을 글자 그대로 쓰고 테스트 배를 가볍게 짓는다 — 추천 설계도(§3.4)도 모두 잠겨 쓸 수 없다.
- **영향:** 계획서 M3 흘수선·침수 줄, M5 목수 공방·`repair` 문구를 고쳤다. 리플레이 형식 v4(규칙 수치 추가).

## ADR-027 물에 잠긴 선실은 쏠 수 없다, 이동 중 발사 입력 막기 (2026-09-29)
- **배경:** M3 코드 리뷰. 흘수선·내려앉기가 들어오면서 선실이 물 아래에 있을 수 있게 됐다(샘플 슬루프는 맨 아래 줄이 늘 잠기고, 3층 선실도 침수 약 73% 부터 잠긴다). 물속에서 쏘면 물보라 위치 계산이 틀어지고, 수직 속도가 중력과 같은 각도에서는 0 으로 나눠 판이 멈췄다.
- **결정 (사용자 결정):**
  - 선실 칸 중심이 잠긴 깊이(흘수선 + 내려앉기, 파도 제외) 이하면 그 해적은 쏠 수 없다(`SideState.canFire`). 파도가 잠깐 선실 중심을 물 아래로 내리면 해수면에서 쏜다. 물보라 계산은 발사점이 해수면 위일 때만 비율로 자른다.
  - 이동 중에 들어온 발사는 이동이 끝난 시각의 파도로 쏜다(ADR-025 그대로). 대신 M4 입력에서 이동하는 동안 당겨서 쏘기를 막아 보이는 파도와 어긋나지 않게 한다.
  - 리플레이 규칙 값 검사를 넓힌다: 폭풍 후퇴 당김 ≤ 20칸, 폭풍·파도·내려앉기·기울기 값 ≥ 0, 격침 비율 0~100.
  - 폭풍 타임에 한계선으로 옮겨진 배는 `move` 이벤트를 낸다.
- **대안:** 발사 위치를 해수면으로 끌어올린다 — 잠긴 선실이 약점이 되지 않고, 수중 계열(§2.1 수중 층)과 뜻이 섞인다.
- **영향:** 사용자 요청으로 설계서 §2.5 에 ‘잠긴 선실’ 문장을 넣고, §7.2 의 `t` 문구를 턴 시각·이동 시간·파도 위상 판정에 쓰도록 고쳤다. 계획서 M4 입력 항목에 한 줄을 더했다. 골든 해시는 바뀌지 않았다.
